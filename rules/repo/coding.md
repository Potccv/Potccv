# 源码编程规范

使用本资料编写或修改源码仓库中的源码时，遵循本文件及[源码仓库入口](AGENTS.md)。维护本文件时，同时遵循[共同写作与核对](../maintenance.md#共同写作与核对)。

## 编程基本原则

- 遵循项目已有的代码风格和组织方式，命名清楚，函数与模块职责明确。
- 严格按用户明确提出的需求实现，采用完整满足需求的最小、直接方案，避免过度工程化。最小指不增加无关功能、抽象或机制，不以改动文件数或行数最少为目标；在授权范围内完成不可缺少的关联修改与适用验证。不要自行补充功能、业务规则或假设性需求；普通实现细节自行选择最简单的合理方案。
- 未经用户明确同意，不增加需求之外的防御性逻辑、安全边界或限制条件，包括数据数量、大小、长度、层级、处理时长上限，以及截断、兜底、重试、降级和兼容分支。不以“更健壮”“更安全”“最佳实践”或“未来可能需要”为由擅自扩展，也不把无依据的限制改成配置项或更大的常量。
- 如确需扩大需求或增加上述逻辑，先说明具体原因、拟增加的行为及影响，取得用户同意后再实施；继续推进不依赖该决定的已授权工作。会话中已有明确授权时，不重复询问。
- 沿用项目现有接口、数据契约和错误处理机制，保证实现正确；不因本约定擅自删除既有校验，不静默吞掉错误或将部分完成报告为全部成功。
- 使用子智能体时，在派发任务中一并传递本约定，并要求其遵守相同的需求范围和授权要求。
- 开发过程中需编写脚本时，优先使用项目采用的编程语言及其工具链，尽量减少 PowerShell（PS）脚本的开发。
- 模块通过公开接口协作，保持依赖方向清晰，避免循环依赖；多个模块需要配合时，优先由上层协调。
- 发现模块过大或职责边界模糊时，应适当提示用户，说明问题并建议按职责边界进行必要拆分。

## 实现边界与复杂度

- 校验按项目既定边界和数据契约执行；内部接口沿用项目已有类型或数据结构。已经由边界可靠保证的条件，不重复检查。
- 每个新增防御分支必须对应可复现失败、现有测试或明确的信任边界；不得以“更健壮”“更安全”“未来可能需要”作为依据，注释、文档或类型声明不能替代失败证据。
- 同一组前置条件只保留一个检查入口；一个生命周期、结果或模式只用一个枚举或类型表达，不用多个可独立组合的布尔字段描述同一状态；派生值计算得出，不重复存储。
- 新接口、抽象、配置项、兼容分支或第二套等价实现必须在任务中写明现实消费者和依据；只有测试替身时优先使用轻量函数指针、模板或直接调用，不为尚未出现的需求预留。一个能力只保留一套 seam。
- 修改完成后，在事项或交付说明中简要说明影响目标、文件职责或接口的实际变化，以及必要验证结果。
- 项目已有明确复杂度标准时按其执行；未定义时不自行补设指标或预算。满足已授权目标所必需的实现变化自主完成，确需扩大需求或增加额外机制时，按[任务范围与冲突处理](../scope.md#任务范围与冲突处理)处理。

## 修改范围

- 修改前检查已有改动，保护用户当前工作。
- 只修改当前任务相关内容，不顺带重构或升级无关依赖。

测试源码与依赖遵循[源码测试要求](testing.md)，验证执行遵循[测试执行与验证](../workspace/testing/execution.md)。编写仓库外的辅助工具时，遵循[本机开发工具](../workspace/tools.md)；子智能体的启用、参数与调度见[子智能体协作](../workspace/collaboration.md)。
