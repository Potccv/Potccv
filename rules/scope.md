# 约束范围与任务边界

本文件补充[根目录执行要求](../AGENTS.md)，按作用范围选择源码仓库或工作区规则，维护规则时另见[共同写作与核对](maintenance.md#共同写作与核对)。

## 规则归属

按[通用规则入口的作用范围](AGENTS.md#按作用范围读取)选择源码仓库或工作区规则。具体执行规则只在所属目录维护；跨范围的任务分别读取所需规则，不因目录分类而扩大操作授权。

## 任务范围与冲突处理

- 在用户已授权的目标内自主完成任务，普通实现细节自行决定；确实需要增加任务或突破用户明确的范围时，才请求确认。
- 根据当前用户请求、会话中仍有效的授权，以及已生效约定和配置中的明确授权确定目标与限制。已有授权直接沿用；AI 自拟的计划、建议或事项记录本身不产生新授权，也不能扩大原授权。
- 动手前自行核实工作区根、源码仓库根，并根据任务目标定位必要文件及允许写入的完整路径或目录范围；范围包括直接编辑、命令生成的输出、移动的来源与目标和删除对象。用户无须逐一列出实现目标所需的文件；明确限定或排除的范围仍须遵守。
- 为实现已授权目标不可缺少的关联修改、既有契约对齐、受影响文档更新和适用验证一并完成。普通实现细节沿用项目约定，选择最简单的合理方案，无须逐项询问；不将可选优化、额外功能或假设性需求当作必要工作。
- 按请求完成相应工作：仅要求检查、审阅或解释时，交付发现与说明；要求修改、修复或实现时，自主完成必要工作。不能自行把检查扩大为修改，也不能把实施任务缩成建议、示例或部分成果。
- 确需增加任务或突破明确范围时，先说明具体原因、拟增加的行为和影响，取得同意后再执行该部分；继续推进不依赖该决定的已授权工作。缺失信息时先查现有上下文和项目资料，只有仍无法确定目标或执行所必需的信息时，才询问该阻塞点，不将普通实现选择交回用户。
- 执行中和收尾时，将实际改动与授权范围比较；区分本次改动与已有或其他协作者的改动，发现越界时停止相关操作并处理偏差。更新通用约束不自动授权修改采用约束的项目文档。
- 约定冲突时先判定各自适用范围，再在平台约束内遵循本轮明确用户指令及仍有效的持续授权；项目专用约定只在其所属范围内生效。
- 只有按上述范围和授权仍无法解决、且阻塞执行的矛盾才询问用户；已有授权足以决定的操作继续执行，无需反复确认。

## 文档位置与适用范围

- 先确认当前任务的工作区根、源码仓库根和目标文件的完整路径。源码仓库通常位于工作区内，因此先判断文件是否属于源码仓库；不能仅凭目录名 `docs`、当前工作目录或文件是否被 Git 忽略来确定归属。
- 本文中的 `<工作区>` 与 `<源码仓库>` 表示已确认的实际根目录，不是相对路径的简写；两者内部的 `docs/` 是不同的维护范围。

| 目标位置 | 用途与执行规则 |
|---|---|
| `<工作区>/docs/`，位于源码仓库之外 | 本机开发说明与事项变化、进度和结果，遵循[工作区开发文档](workspace/docs.md) |
| `<源码仓库>/docs/`，以及仓库内的 README、模块说明、CONTRIBUTING 和 AGENTS | 随源码维护的项目说明、接口与使用文档，遵循[源码仓库文档](repo/docs.md) |

- 工作区事项的状态目录、文末时间、原位覆盖与过期旧文件清理规则仅在其规定的工作区范围内执行，不自动套用到源码仓库文档。
- 维护一类文档不自动扩展到另一类，不因同名目录而跨范围创建、移动或删除文件。

## 交付说明

- 简要说明修改的是工作区文档还是源码仓库文档，并报告实际改动、验证结果和遗留问题。
