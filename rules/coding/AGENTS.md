# AGENTS.md — 编程与设计

使用本资料明确需求、设计模块、编写或重构源码时，遵循本文件及[根目录执行要求](../../AGENTS.md)。维护本目录文档时，同时遵循[通用约定文档的维护要求](../AGENTS.md)。

编程任务先掌握[基本原则](#基本原则)和[需求与验收](#需求与验收)，再按改动选择设计、实现或重构章节。接口、数据、安全、依赖和运行细则分别维护在相邻领域，不要求为每次小改动阅读全部规范。

## 基本原则

- 先保证行为正确、数据安全和兼容性，再追求易读、易改和性能；发生冲突时，说明具体约束与取舍。
- 遵循所属项目已采用的语言惯例、目录结构和工具配置。格式化、静态检查与类型检查能自动完成的要求，交给工具统一执行。
- “必须”“不得”“禁止”表示适用场景下的要求；“优先”“建议”“按需”表示需要结合成本和收益判断的建议。有条件的条目只在对应条件成立时适用。
- 规则强度与改动风险匹配：文案修正、内部计算调整、支付处理和生产数据迁移不采用同一套交付负担。项目特殊约束及例外按[状态记录](../docs/AGENTS.md#状态记录)保存，不推广成所有项目的规则。
- 采用当前需求所需的最小充分设计。没有实际需要时，不引入微服务、通用框架、复杂继承、插件系统或多层转发。
- 先理解再修改，优先复用项目内已有且语义匹配的实现；不为统一个人风格改写无关代码，不顺手扩大任务范围。
- 不编造已经存在的文件、接口、工具能力或验证结果。生成的代码和引用的示例都需要结合实际版本、调用方和运行环境核实。

## 需求与验收

- 开始实现前，明确使用者、触发条件、预期结果和本次不处理的范围；简单任务可在任务说明中写清，不要求额外创建需求文档。
- 找到当前行为的依据：实际源码、接口契约、已有测试和可复现结果。将已确认事实与尚未证实的推断分开。
- 用可观察的结果描述验收条件，至少覆盖主要成功路径及与改动有关的失败、边界情形。例如“重复请求只生成一笔订单，返回同一业务结果”，比“优化下单逻辑”更明确。
- 对时延、吞吐、可用性、数据保留期、兼容设备等非功能要求，只有在确有要求时给出指标、测量条件及允许范围，不凭空承诺数值。
- 有歧义时先查项目资料和已有行为；普通实现细节自行判断并记录必要假设。会改变业务语义、数据去留或权限边界的缺失信息，应在实施依赖该信息的操作前澄清。
- 修复缺陷时先定位触发条件和根因。无法稳定复现时说明现有证据和验证范围，不把猜测写成已确认原因。

## 架构与模块边界

- 按业务能力或清晰职责划分模块，使经常一起变化的代码靠近；每个模块有明确输入、输出、依赖和状态归属。
- 模块只公开调用方需要的最小接口，内部数据结构和实现细节保持私有；避免跨模块直接修改彼此的内部状态。
- 依赖方向保持清晰，避免循环依赖。复杂业务中，可将业务规则与数据库、网络、UI 等易变细节分离，使核心行为能够独立理解和验证。
- 只有出现真实替换需求、外部依赖隔离需求或多种实现时，才考虑接口层、适配器和依赖注入；不要求每个类都有一个同名接口。
- 优先组合明确的能力；继承用于稳定且可替换的类型关系，避免深层继承和改变父类约定的子类。
- 一个事实或业务规则应有明确维护位置。提取重复代码前，确认其业务语义和变化原因相同，避免把外观相似但职责不同的逻辑强行合并。
- 对有生命周期的对象明确合法状态和转换条件，例如订单是否允许从“已取消”回到“待支付”；涉及跨进程一致性时按[数据与存储](../data/AGENTS.md)处理。
- 只有确实涉及长期成本、兼容性或难以撤销的选择时，记录决策背景、候选方案、取舍和复审条件；记录位置遵循[文档职责](../docs/AGENTS.md#文档职责)。

## 命名与表达

| 对象 | 要求与示例 |
|---|---|
| 变量与字段 | 表达业务含义，避免无上下文的 `data`、`info`、`tmp`；例如 `remainingRetryCount` 表达剩余次数 |
| 布尔值 | 表达可判断的状态，如 `isExpired`、`canEdit`；避免双重否定和含糊的 `flag` |
| 函数与方法 | 表达动作及结果，例如 `loadInvoice`、`calculateTotal`；名称应让调用方理解是否存在写入或外部调用 |
| 单位与范围 | 单位不由类型表达时显式标注，如 `timeoutMs`；明确边界是否包含端点，避免毫秒与秒混用 |
| 常量与枚举 | 为具有业务意义的固定值命名；枚举外部值的解析要处理未知值，不能默认为成功状态 |

- 具体采用 `snake_case`、`camelCase` 或其他风格，由项目和语言惯例决定；同一作用域、同类概念保持一致。
- 只使用团队和领域普遍理解的缩写；同一概念保持同名，不同概念避免共用名称。
- 注释解释为什么、限制和不明显的边界，不逐行翻译代码。对公共接口记录参数、返回值、副作用、错误、单位和并发约束中实际需要的部分。
- 不保留大段注释掉的废弃实现；版本历史交给 Git。确需保留的 `TODO` 应说明具体问题、影响和跟踪位置，不能充当验收完成的替代品。

## 函数与控制流程

- 函数承担一个可描述的主要职责；当理解一个函数需要同时记住多组独立状态时，考虑按职责拆分，不以固定行数机械切割。
- 优先使用清晰的分支、提前返回和有名的中间变量；避免深层嵌套、复杂三元表达式以及依赖运算优先级猜测含义的写法。
- 参数过多或存在多个含义不明的布尔参数时，考虑有字段名的参数对象、枚举或职责拆分；参数对象仍需保持明确边界。
- 默认值必须符合业务语义，不能用 `0`、空字符串或空集合掩盖读取失败、配置缺失或权限拒绝。
- 查询和修改的副作用应可预期。不得在名称表现为普通读取的函数中隐式执行付款、删除或长时间阻塞操作。
- 使用工具统一格式后，只保留与本次任务相关的差异；不要把全仓库格式化和业务修复混为一项改动。

## 类型与边界值

- 在外部输入边界检查类型、范围和结构；静态类型声明不替代运行时输入验证。内部使用已经验证的明确类型，减少到处重复解析。
- 区分“缺失”“显式为空”“空集合”“零”“失败”等状态，避免依靠真假值判断丢失业务语义。例如金额 `0` 可以是有效值，不能直接视为未填写。
- 金额使用符合业务精度要求的十进制定点数或整数最小单位，并明确币种及舍入规则；不直接依赖二进制浮点数完成精确账务计算。
- 标识符、数量、偏移量和累计值考虑范围、溢出及跨语言传输精度；例如 JavaScript 无法精确表示所有 64 位整数，接口应约定安全的表示方式。
- 时间点、当地日期和持续时长使用不同语义；序列化、时区、夏令时与存储约定见[数据表示](../data/AGENTS.md#数据表示)。
- 涉及文本时，明确编码、大小写比较和 Unicode 处理规则；字符数、字节数和用户可见字符数不能随意互换。

## 错误与资源管理

- 区分预期业务失败、输入错误、外部依赖故障和程序缺陷；采用语言或项目统一的异常、结果类型或错误返回约定。
- 在能够处理问题的层级捕获错误。不得空捕获、把异常一律转换为成功、用默认值隐藏故障或反复捕获后丢失原始原因。
- 包装错误时保留原因链和必要上下文；对外错误契约见[错误契约](../interfaces/AGENTS.md#错误契约)，日志记录与脱敏见[运行与发布](../operations/AGENTS.md#日志指标与追踪)。
- 获取文件、连接、锁、事务和临时资源后，必须通过语言支持的作用域、`finally`、`defer`、上下文管理器等机制保证释放，覆盖异常和取消路径。
- 说明资源和缓冲区的所有权，避免重复释放、悬空引用、忘记关闭连接和无限增长的内存缓存。
- 配置或内部状态违反必要前提时尽早给出明确错误；断言可检查内部不变量，但不能作为生产环境外部输入验证的唯一机制。

## 并发与异步

- 引入并发前先确认收益和共享状态，明确最大并发数、排队上限、资源成本及取消方式。
- 优先减少共享可变状态。确需共享时使用匹配场景的锁、原子操作、消息传递或数据库约束，不假设“先检查再写入”天然原子。
- 避免持有锁执行网络请求或未知耗时操作；需要多把锁时保持一致的获取顺序，并明确发生取消时如何释放。
- 异步任务必须有生命周期归属，等待或明确管理其完成、失败和取消；不让未观察的后台异常静默丢失，也不把阻塞工作放进事件循环关键路径。
- 一次请求的截止时间和取消信号应传递给子操作；结束等待不代表外部写入已经撤销，重试策略见[超时重试与幂等](../interfaces/AGENTS.md#超时重试与幂等)。
- 并发操作不得依赖未经保证的执行顺序。结果顺序有要求时显式排序或汇合，测试覆盖竞态和部分失败。

## 用户界面与交互

- 有 UI 时，为加载、空内容、失败、无权限、成功和重复操作设计必要状态，保持反馈与真实处理结果一致。
- 客户端输入校验用于改善体验，服务端仍须执行必要校验和授权；防止重复点击不能替代服务端幂等处理。
- 优先语义化控件，支持键盘操作、可见焦点、可读标签及合理对比度；不能只依赖颜色传递状态。
- 依据实际目标设备处理布局、缩放、国际化、时区和长文本；没有多语言需求时不强行增加完整国际化体系。
- 仅有确定恢复机制时使用乐观更新，失败后给出可理解的恢复路径。涉及 UI 的验证遵循[开发与验证](../testing/AGENTS.md#开发与验证)。

## 修改与重构

1. 检查工作区已有改动、调用方和相关约束，保护与任务无关的用户工作。
2. 先明确受影响的行为和验证方式；涉及数据、协议或安全边界时读取对应规范。
3. 以可理解的小步骤完成必要变更；重构尽量保持外部行为，确需改变行为时在验收条件中写清。
4. 同步更新受影响的配置示例、接口说明和测试；是否新增测试按[验证范围](../testing/AGENTS.md#验证范围)判断。
5. 完成必要检查并审阅最终差异；发现无关问题时记录或说明，不未经授权扩大改动范围。
6. 交付时说明改动结果、实际验证和未解决事项；版本与提交遵循[版本与授权](../git/AGENTS.md#版本与授权)。
