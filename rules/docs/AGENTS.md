# AGENTS.md — 文档与资料

使用本资料编写文档、整理资料或记录状态时，遵循本文件及[根目录执行要求](../../AGENTS.md)。维护本目录时，同时遵循[通用约定文档的维护要求](../AGENTS.md)。

文档任务先掌握[文档职责](#文档职责)和[写作与维护](#写作与维护)；涉及项目资料归档时再读[资料存放位置](#资料存放位置)，记录进展或验证结论时再读[状态记录](#状态记录)，交接或管理待办时再读[事项管理](#事项管理)，说明交付结果时再读[交付说明](#交付说明)。

## 文档职责

以下采用 DSH 的通用分层方式，按内容和目录职责选择所需文档，不要求每个目录同时创建 AGENTS.md 与 README.md。所属项目已有约定时遵循其约定；Potccv 的专属要求见[维护本项目](../../AGENTS.md#维护本项目)。

| 文件 | 职责 |
|---|---|
| 根目录 AGENTS.md | 每次任务需要的常驻要求；条目简短自洽，链接到详细说明，不展开情境操作步骤 |
| 目录级 AGENTS.md | 该子树特有的执行或维护要求，不复述上层已有规则；有此类要求时再建立 |
| README.md | 所属项目、目录或模块的介绍、用途、使用方式、配置语义、限制及导航 |
| 架构与参考文档 | 分别维护整体组成关系与所属主题的详细定义、语义和接口，不越级展开子模块细节 |
| 教程、操作指南与开发文档 | 按前置条件和步骤说明如何完成任务，包含所需验证；简短内容可在所属文档中单设章节 |
| 决策与事故记录 | 保存决策背景、权衡或事件证据，避免在常驻指令和使用说明中叙述历史 |
| JSON 配置、忽略规则等机器可读文件 | 保存实际字段结构、格式版本、匹配模式等数据；文档引用这些文件，不另行维护一份清单 |

- 正式源码仓库的项目说明应在仓库内自足，不以仓库外的本机资料或某次产物作为读懂项目的前提。本机任务的操作记录和真实数据路径放在工作区 `docs/`，并引用仓库或工具的正式说明；参数化的外部输入、可配置输出示例及其他合理的相对链接仍可使用。

## 写作与维护

- 同一事实只保留一个维护位置，按[文档职责](#文档职责)归入对应文档或数据文件，其他位置通过相对 Markdown 链接引用。
- 上层文档介绍直接子目录的用途、适用条件与入口；领域细则按独立职责和使用时机组织，共用要求留在适用范围覆盖各子目录的 AGENTS 中。
- 文档描述当前事实，保留原有条件、授权范围和例外；未提供或未核实的信息明确标注。
- 现行开发说明在固定的主题文件内原位覆盖更新；用法变化时同步改写对应正文和示例，使当前说明反映有效用法，不另建日期版、最新版或副本来并行维护同一用法。
- 更新后检查旧说明和副本；已过期且被新说明完整替代的文件，在确认仍有效的内容、未关闭事项、授权限制和必要证据已保留后清除，并同步更新导航和引用。历史验收记录与完成事项按各自保留要求处理，不仅凭日期较早就判为过期。
- 参考内容按主题组织，操作教程按步骤组织；较短的教程使用明确的小节标题，避免在目录页展开细节。
- 新增、移动或删除文档时，同步更新已有导航、相关 AGENTS 入口和受影响的引用。
- 文档变更后核对链接、标题锚点与示例，只报告实际完成的验证。

## 资料存放位置

目录分类遵循[目录职责](../workspace/AGENTS.md#目录职责)，具体资料按下表归档；已有同职责目录可沿用，不为统一名称自行全量迁移。同一事实只在对应位置维护，其他文档引用它。

| 资料 | 位置 |
|---|---|
| 项目概览、架构、接口、使用说明和可共享开发规范 | 待推送到 GitHub 的项目目录内，例如其中的 `docs/`，随项目维护 |
| 项目版本、任务进展、部署与验证结论、授权例外和交付历史 | 可公开内容随项目维护；仅供本机使用的人可读记录归入工作区 `docs/`。记录方式见[状态记录](#状态记录) |
| 本机方案、任务操作记录、协作记录、私有运维资料和文字验证结论 | 工作区 `docs/`，按项目或用途分类；敏感资料不写入公开项目文档 |
| 程序快照、需保留的原始构建或测试证据、交付物及冻结快照 | 按[目录职责](../workspace/AGENTS.md#目录职责)归入工作区 `artifacts/`，文档引用其位置；可再生成的构建输出归 `build/`，短期文件归 `tmp/` |
| 原始素材、数据集和完整原始采集会话 | 工作区 `data/`；会话内的记录与附件一并保留，不按文件扩展名拆散 |
| 本机长期辅助工具源码 | 工作区 `tools/`，用途和操作说明可在 `docs/` 引用 |
| 个人配置与凭据 | 按[凭据与发布要求](../../profile/AGENTS.md#凭据与发布)存放 |

需要从个人配置查找资料路径时，见[个人配置字段](../../profile/AGENTS.md#字段职责)；资料导航按[文档职责](#文档职责)组织。人可读文档目录不作为安装包、SDK 或源代码快照的堆放位置，也不要求每个临时文件配备 README。本仓库不集中收纳其他项目的资料目录。

## 状态记录

- 需要交接或持续跟踪的任务按[事项管理](#事项管理)维护唯一事项文件，记录当前使用版本、实际验证范围、待办、持续授权和限制；README、概览和跨事项主题入口只提供导航与关联，不重复维护单个事项的进度。
- 源码、部署和验收状态分别记录最后核验时间；搬移文档不更新实测日期。章节排序、版本号和源码推送均不构成实际部署结果的证据。
- 历史记录保留当时的事实、日期和限制，并链接后续状态入口；阶段证据按[资料存放位置](#资料存放位置)保留。

## 事项管理

- 将交接中的未完成工作按可独立验收的事项拆为文件，默认放在工作区 `docs/tasks/待办事项/`。一个功能或问题对应一个事项，实施步骤使用文件内的检查清单，不为每个小步骤单独建文件；长期约定、设计依据和操作限制留在对应文档，由事项引用。
- 文件使用稳定且唯一的编号和表达用途的名称，例如 `T001-开发工具独立运行.md`；创建前检查待办与完成目录，避免编号冲突或重复建项。待办文件中的状态为“待开始”“进行中”“受阻”或“待验证”。
- 每个事项写明目标、工作清单、验收条件、当前进展与接续、关联资料；需要其他事项先完成时引用其编号和路径。该文件是对应任务进度和接续信息的唯一来源，不再在总交接或另一份待办清单重复维护正文。
- 实现完成且适用验证通过后，补充完成结果与验证证据，将状态改为“已完成”，把原文件移入 `docs/tasks/完成事项/`，保持编号和文件名，并同步更新导航及其他事项中的路径引用。同一事项不在两个目录中各留一份。
- 时间记录放在事项文档最末端，正文和关联资料均位于时间记录之前。未完成事项保留“创建时间”“最后更新时间”两行；完成时在最后追加“完成时间”，作为文档最后一行。
- 事项时间使用任务所属时区的 24 小时制，格式统一为 `yyyy-mm-dd hh:mm:ss`，精确到秒，不附加时区后缀或毫秒。创建时间固定不变，最后更新时间随正文或状态变更更新，完成时间记录实际达到验收条件的时刻，不因后续归档或移动而改写。
- 拆分旧交接时保留原验证日期、授权限制和未关闭事项；新事项文件的创建时间取实际创建时刻，历史完成时间无据可查时标注“未记录”，不以迁移时间冒充完成时间。

事项文件按以下结构维护，时间占位符须替换为实际值：

```markdown
# <事项名称>

状态：待开始

## 目标
<预期结果>

## 工作清单
- [ ] <实施步骤>

## 验收条件
<可核验的完成标准>

## 当前进展与接续
<已完成工作、阻塞点和下一步>

## 关联资料
<设计依据、相关事项、源码和验证证据的链接>

---
创建时间：yyyy-mm-dd hh:mm:ss
最后更新时间：yyyy-mm-dd hh:mm:ss
```

完成时在文末追加 `完成时间：yyyy-mm-dd hh:mm:ss`，其中时间替换为实际完成时刻。
